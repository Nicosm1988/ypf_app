DATALIZA · DATA E IA · PROPUESTA PARA EVALUACIÓN INTERNA

Edición simultánea sin sobrescribir el trabajo del equipo

Propuesta: centralizar el guardado de Dataliza en un servicio instalado en una PC Windows, con una base de datos local y acceso del equipo desde el navegador.

La necesidad es que varios usuarios puedan consultar y editar al mismo tiempo, tanto en Data como en IA, conservando los cambios de cada persona y las exportaciones para Power BI.

Por qué hace falta el cambio

Actualmente, cada navegador trabaja con una copia de la base. Al guardar, la aplicación reemplaza el archivo JSON completo del área, aunque se haya modificado una sola tarea. Ese mecanismo no coordina de forma fiable las escrituras desde distintas computadoras.

NecesidadSituación actualResultado buscado
Editar tareas diferentes a la vezUna copia completa puede reemplazar cambios ajenos.Guardar cada operación sobre el registro correspondiente.
Editar la misma tareaHay detección parcial de conflictos, sin coordinación central.Detectar la versión desactualizada y pedir revisión antes de reemplazarla.
Conservar información para gestiónLos respaldos permiten recuperar versiones, con revisión manual.Prevenir sobrescrituras y mantener respaldos para otros incidentes.

Qué se propone y qué se conserva

Se propone adaptar la aplicación para que un único servicio reciba las operaciones, valide los datos y confirme cada guardado. Se conservarían la experiencia de uso, las áreas Data e IA y sus exportaciones para Power BI.

No se requiere instalar una aplicación en cada PC del equipo: los usuarios accederían a una dirección interna desde Chrome o Edge. La PC anfitriona alojaría la aplicación y los datos.

Estado de la propuesta: el servicio central y la migración todavía no están desarrollados ni instalados. Este documento solicita evaluar la viabilidad y autorizar un piloto; no describe una solución ya desplegada.

Fecha: 22 de septiembre de 2026 · Alcance: arquitectura de edición compartida de Dataliza.

02 · EJEMPLO DEL PROBLEMA

Dos personas cambian tareas distintas y un cambio puede perderse

Ana y Bruno abren Dataliza a las 9:00. Ambos ven la tarea A “En curso” y la tarea B con vencimiento el viernes.

MomentoQué ocurre
1. Ana edita AMarca la tarea A como “Finalizado”. Su copia conserva B con vencimiento el viernes.
2. Bruno edita BCambia el vencimiento de B al lunes. Su copia todavía conserva A “En curso”.
3. Ana guardaSu PC escribe la base completa: A finalizada y B con vencimiento el viernes.
4. Bruno guardaSi el conflicto no se detecta, su copia completa reemplaza la anterior: B queda para el lunes, pero A vuelve a “En curso”.

Resultado posible: el cambio de Ana deja de estar en la base principal, aunque Bruno nunca haya editado la tarea A.

Qué protección existe hoy

La aplicación compara la base antes de escribir e intenta bloquear guardados sobre una versión desactualizada. También conserva respaldos. Son controles útiles, pero no garantizan coordinación entre computadoras: dos guardados casi simultáneos pueden pasar las verificaciones, y una carpeta sincronizada puede demorar en mostrar los cambios de otra PC.

Si se detecta el conflicto, el segundo guardado se frena y requiere actualizar y revisar. Si no se detecta, puede ser necesario buscar el cambio en los respaldos y reconstruirlo manualmente. La pérdida no ocurre en cada guardado, pero el mecanismo actual permite ese escenario.

Cómo funcionaría con el servicio central

Ana envía el cambio de la tarea A y Bruno el de la tarea B. El servicio guarda ambas operaciones sobre sus respectivos registros. Ninguno reemplaza la base completa del otro.

Si ambos editan A, cada solicitud incluye la versión que la persona abrió. El servicio verifica esa versión y actualiza el registro en una misma transacción. Tras guardar el primer cambio, rechaza el segundo si quedó desactualizado.

Mensaje esperado: “Otra persona modificó esta tarea. Revisá la versión actual antes de guardar”. La interfaz debe conservar la edición pendiente para que el usuario pueda compararla y decidir. No se propone una fusión automática de campos.

03 · SOLUCIÓN PROPUESTA

Una PC coordina; el equipo utiliza el navegador

PCs del equipo → red interna o VPN → servicio Dataliza en la PC anfitriona → base SQLite en disco local.

ComponenteUbicación y función
Python y dependencias de la aplicaciónEn la PC anfitriona. Ejecutan el servicio web; la versión y los paquetes se definirán y aprobarán para el entorno corporativo.
Servicio web DatalizaEn la PC anfitriona. Entrega la interfaz, valida solicitudes, coordina guardados y registra resultados. Debe poder arrancar automáticamente y recuperarse de fallas.
Base SQLiteArchivo local en la PC anfitriona. No requiere instalar un servidor de base de datos separado. El servicio accede a ella mediante el módulo sqlite3 de Python [1].
NavegadorEn cada PC usuaria. Accede al enlace interno; no abre directamente la base de datos.
Respaldo y exportacionesEl servicio debe generar copias verificadas y exportaciones de Data e IA para los destinos autorizados.

Por qué SQLite puede servir para el piloto

SQLite permite múltiples lectores y una escritura a la vez. El servicio puede atender a varios usuarios y coordinar operaciones breves; la experiencia de edición simultánea no exige que todas las escrituras físicas ocurran en el mismo instante. Su adecuación debe comprobarse con el volumen real del equipo [2, 3].

La base activa debe quedar en disco local, fuera de OneDrive y carpetas de red. Los usuarios acceden mediante el servicio; no comparten el archivo SQLite directamente. Si el volumen o la disponibilidad exigida crecen, se deberá evaluar un servidor administrado y otra base de datos [2].

Autenticación y disponibilidad

Resolver la concurrencia no exige integrar primero el inicio de sesión con Microsoft. La selección de nombre podría conservarse para un piloto si Sistemas la acepta, pero seguiría siendo una identidad declarada, no verificada. El acceso y la autenticación para uso operativo deben acordarse por separado.

La PC anfitriona es un punto único de disponibilidad: si se apaga, suspende, reinicia o pierde conectividad, el equipo no podrá consultar ni guardar contra el servicio. No se propone edición desconectada ni sincronización posterior automática.

La base de datos evita ciertos errores de concurrencia, pero no sustituye los respaldos. Se deben generar copias consistentes con un mecanismo compatible con SQLite y verificar su restauración; no basta con copiar a ciegas el archivo mientras está en uso.

04 · IMPLEMENTACIÓN Y DECISIÓN

Qué hay que hacer para ponerlo en marcha

Paso y responsableResultado necesario
1. Viabilidad · SistemasConfirmar que se permite alojar el servicio en la PC Windows. Definir dirección estable, puerto, alcance de red/VPN, firewall, protección de la conexión y acceso autorizado. Sin exposición pública a Internet.
2. Adaptación · DesarrolloCrear el servicio, persistencia por registro, validaciones y control de versión atómico. Adaptar la interfaz para manejar conflictos, errores y actualización de datos desde el servidor.
3. Operación · Sistemas y responsable de DatalizaConfigurar arranque automático, recuperación tras reinicio, horario de disponibilidad, registro de errores, respaldo independiente y responsable de soporte.
4. Migración · Responsable de datos y DesarrolloRespaldar los JSON de Data e IA, detener temporalmente las ediciones e importar los datos. Comparar tareas, catálogos, comentarios e historial; conservar los originales.
5. Piloto · Equipo usuarioValidar desde dos PCs los casos de concurrencia, conectividad, recuperación y Power BI antes de habilitar el uso general.

Criterios para aceptar el piloto

  • Dos usuarios editan tareas diferentes y ambos cambios se conservan.
  • Dos usuarios editan la misma tarea: se detecta el conflicto y se conserva la edición pendiente del segundo usuario para revisión.
  • Una interrupción de red no produce una confirmación falsa; los reintentos no duplican operaciones como comentarios.
  • Tras reiniciar la PC, el servicio vuelve a estar disponible y conserva los datos confirmados.
  • Se restaura un respaldo en un entorno de prueba y se comprueba su contenido.
  • Se regeneran y cargan las tablas de Data e IA en Power BI, manteniendo identificación de área y relaciones correctas.

Las exportaciones actuales tienen 7 dimensiones y 4 tablas de hechos por área, con area_id, area_nombre y claves por área. La adaptación debe conservar ese contrato y publicar conjuntos consistentes. El refresco programado de Power BI Service, si se requiere, se evaluará por separado.

Decisión solicitada: aprobar la evaluación técnica y un piloto en una PC designada, con responsables de operación y respaldo. Si la política corporativa no permite alojarlo allí, evaluar un servicio interno administrado que mantenga el mismo mecanismo central de guardado.
